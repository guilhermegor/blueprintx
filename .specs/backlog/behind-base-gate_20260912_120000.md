# Behind-base gate report (blueprintx#368)

## Problem

A PR runs every gate script from its own checkout. A branch behind `main` therefore runs an
OLD copy of a gate (e.g. `templates/common/bin/check_review_threads.py`), and can fail — or
wrongly pass — for a reason that has nothing to do with the PR's own diff. `gh pr
update-branch` fixes the gate version but moves the head commit, which can flip an
already-clean review to SUPERSEDED (a review is pinned to the commit it was written against
and nothing re-pins it). That is a deadlock, not a delay.

## Decision

Automate the DATA half only: report, for every open PR, whether it is (a) behind `main` and
(b) judged by a gate file that changed on `main` since the PR's merge-base — paired, not
separately, closing the loop gap the issue names. Do **not** auto-run `update-branch`: which
PR is worth spending a review-quota unit on (re-review after the branch moves) is a judgment
call, left explicitly to a human. This is the "report the staleness and let a human choose"
option from the three offered, chosen because the other two ("update only if otherwise
mergeable", "update only if gate moved") both still end in an automated `update-branch` —
and the coordinator's own measurement (merging main into #444 flipped its review from OK to
SUPERSEDED) shows that action consumes the same scarce review-quota resource the rest of the
loop is optimizing for. The decidable half (behind + gate-diff) is exactly what's automated;
spending the quota is not.

- Confirmed the SUPERSEDED evidence directly: merging `main` into #444 moved its head and the
  gate flipped from `OK` to `SUPERSEDED` in one step — the 3 previously-answered threads
  stayed `unresolved=0`, but no review is attributed to the new head. This is the second half
  of the deadlock, reproduced.
- Read `review_retry.yml`'s own measurement before proposing a schedule: a `*/10` cron fired
  6 times in 21 hours on this repo (GitHub throttles scheduled workflows hardest on
  low-activity repos). This report is advisory-only (never blocks a merge), so it uses a
  coarse `0 */6 * * *` schedule plus `workflow_dispatch` — a tight interval buys nothing here
  since nothing is waiting on it, and a coarse one is far less exposed to the same throttle.
