# Issue waves — grouping 49 open issues by blast radius

Created 2026-08-23. Ledger for the wave programme that drains the open-issue queue.

## Where each thing lives (and why it lives there)

This file is **not** the list of issues in each wave. GitHub milestones are, and they update
themselves when an issue closes:

```bash
rtk gh issue list --milestone "Wave A — gates that lie"
```

Three stores, three questions, no duplicated list:

| Store | Answers | Self-updating |
|---|---|---|
| Milestone | which issues are in a wave, how many remain | yes |
| **This file** | why this grouping, what order is mandatory, what was learned per slice | no — but it changes rarely |
| Kanban (project 8) | per-issue status | per issue, orthogonal to waves |

The kanban deliberately does **not** carry wave grouping. A third copy of the same membership
list is the defect `bin/ci/check_codespell_sync.sh` exists to police: two lists identical on the
day they are written, and nobody knows which is right on the day they differ.

## The grouping axis: shared files, not shared commit prefix

The original proposal was to batch by conventional-commit type — all `python-common` in one PR,
all `chore` in another, all `ts-*` in a third. Rejected, measured against the real queue:

- The `python-common` bucket holds **18** issues. #231 showed a review finding two Major defects
  in a PR with 33 green checks; at 18 issues nobody finds anything.
- The `chore` bucket mixes the CI reviewer roster (#234), a codespell prune (#197) and a CLI
  investigation (#230) — zero shared files, so zero amortised rebase/lint/scaffold-test cost.
- `Closes #N` accounting degrades with PR size (measured: PR #170 declared 7, closed 1).

The cost that actually amortises is rebase + `poe lint` + `bin/ci/scaffold_lint_test.sh` across
five tiers. That only amortises when the issues touch the **same files**. Hence: blast radius.

The one bucket from the original proposal that survives unchanged is `ts-lib` (#132–#136) — it
was already coherent, because it is one skeleton rather than one prefix.

## Waves

### Wave A — gates that lie  ← in progress

`templates/python-common/bin/` + `.pre-commit-config.yaml`. Every issue here is the same failure
mode: **a gate that reports success without having run.** That mode has no symptom, which is why
it is first.

- [x] #237 — `poe lint` does not run every gate pre-commit runs — **done**, 5/5 tiers green
- [x] #244 — 29 functions fail `check_typing` — **done**, both gates now in `lint.sh`
- [x] #246 — 6 `__all__` violations block `check_all_exports` — **done**
- [x] #254 — `check_complexity.sh` dies on a coloured ruff output — **done**, 5/5 tiers green
- [x] #111 — venv cache disables the install gate; should-fail tests for every gate — **done**
- [ ] #238 — adopt `deptry` (the direct-dependency rule is prose with no gate)

**What #111 measured.** Two corrections to the issue's own numbers, both found by re-running the
audit instead of trusting it:

- **Part 1 (the `tests.yaml` venv cache) was already delivered by #170** (`ac069c3`) and simply
  never ticked — the "declared 7, closed 1" accounting gap this ledger already describes, seen
  from the other side. All three coupled defects are in the tree today with in-file comments.
- **The uncovered-gate count was 9; it is 8.** `check_dtypes.py` does have a real should-fail
  witness (`returncode == 1` on a banned dtype), inside a test whose stated purpose is stdout
  encoding. The other three `.py` gates appear in that file only as *names in a parametrize list*
  for a stream-reconfiguration sweep — covered-looking and not covered, one level deeper than the
  trap the issue already called out.

**Writing the eight witnesses found three live defects**, which is the argument for the rule
rather than a coincidence: `check_provenance.py` and `check_docstrings.py` both exited 0 printing
**nothing** when their cwd-relative globs matched nothing, and `lint_actions.sh` (plus
`lint_shell.sh`) accepted any file named for the tool on `PATH` as a working one — its own comment
claimed a `--version` probe that existed only on the poetry branch. A stub exiting 127 produced
`actionlint [system]: 7 workflow(s)` then exit 127, blaming the workflows for the tool's failure
to start.

⚠️ **The wrappers root at `$SCRIPT_DIR/..`, not the cwd.** `main()` opens with
`cd "$SCRIPT_DIR/.."`, so a test that only sets `cwd` audits `templates/python-common` instead of
its fixture — measured, a one-workflow fixture reported `7 workflow(s)`. Their tests must copy
`bin/` into the fixture tree. This is most of why these five had no tests.

**Tool-absence is made deterministic by shadowing, not by skipping.** A stub first on `PATH` that
exits non-zero for `--version` reproduces "absent" on any machine — including CI, where the real
tools ARE installed and where the `*_REQUIRED` contract matters most. A `skipif(which(tool) is
None)` would have dropped that coverage exactly where it counts.


**What #237 actually cost, and why the wave grew.** Wiring six pre-commit-only gates into
`bin/lint.sh` made them run, for the first time, against a real generated project — and two of
them immediately went red on pre-existing debt (#244: 28 functions; #246: 6 exports across 3 of
5 tiers). Both were held out behind a comment in `lint.sh` naming their issue and an explicit
do-not-re-add note, rather than folded into the wiring commit: wiring a gate and paying its debt
are different changes with different risk (#244's includes `@functools.singledispatch` handlers
where the decorator changes per-cell runtime cost).

**What paying that debt measured** (#244/#246). Both gates are now in `lint.sh` and all five
tiers are green. Three things were settled by measurement rather than argument:

- **`@functools.singledispatch` + `@type_checker` compose**, with `.register` outermost:
  probed `int→int`, `str→str`, `None→fallback`, and the checker still raises `TypeError`.
  `.register` reads the annotation through the wrapper because `functools.wraps` preserves
  `__annotations__`. This was the issue's blocking unknown.
- **Per-cell cost is 2.16x — 0.85 µs, or 0.85 s per million cells.** Small enough that building
  an exemption mechanism into `check_typing.py` would have been more machinery than the number
  justifies, so all 29 were decorated instead.
- **A `T` can be dead and a `T` can be load-bearing**, twenty files apart. In
  `db_schema/infrastructure/base.py` the `TypeVar` was declared and never used (`Repository`
  annotates `Any` throughout) → deleted with its now-orphaned import. In `ports/example_port.py`
  it is `Generic[T]` and the port's whole point → renamed `_T`, the typeshed convention for a
  variable an adapter parameterises but never imports. Neither fix is "add it to `__all__`".

⚠️ **A 29th violation surfaced in a file the first sweep did not reach**: `lib-minimal/main.py`.
The sweep ran over `python-common/src/utils/`, which is where 28 of them lived; the lib tier
ships its own entry point. This is the forgotten-tier failure mode #230 names, and it was caught
only because the gate now runs against a real scaffold of *every* tier.

Its fix carries a note worth keeping: `main.py` needs a **relative** import
(`from ._internal.utils.typing import type_checker`) because `rewrite_internal_imports` rewrites
`utils.` → `<pkg>._internal.utils.` only inside `_internal/`, and this file is copied outside it.
A bare import would ship unrewritten; an absolute one cannot be written, since `<pkg>` is known
only at scaffold time. The reason is in the file, so the next reader does not "fix" it back.

**What #254 measured, and why the issue's own proposed fix was wrong.** The issue proposed
`NO_COLOR=1`. Measured against ruff 0.11.13: **`NO_COLOR` does not win against `FORCE_COLOR`** —
the forcing variable takes precedence, and `TERM=dumb` does not change it either. A fix written
as the issue specified would have left the defect live behind a green test. The gate now runs
ruff in a subshell that **unsets** `FORCE_COLOR`/`CLICOLOR_FORCE` (a subshell rather than
`env -u …`, because the poetry branch calls a shell *function*, which `env` cannot exec; and
rather than `local`, which does not hide an exported global from a child — both measured).

Two further findings from that slice:

- **The audit found exactly one exposed wrapper.** `lint_shell.sh`, `lint_sql.sh`,
  `lint_yaml.sh`, `lint_actions.sh` and `lint_docker.sh` only read exit codes; `check_complexity.sh`
  is the only gate that parses a linter's stdout into fields. So the blast radius was one file,
  not the five the issue anticipated.
- **The should-fail test already existed in the right place, and was itself colour-dependent.**
  `tests/integration/test_bin_scripts.py` already carried nine complexity-gate tests — a
  standalone unit-test module for the same gate was written and then deleted as duplication.
  What was missing was narrower: `_run_complexity` inherited the ambient environment, so the
  suite's verdict depended on the developer's shell. It now strips the colour variables and
  takes an explicit override, which is what let the four new tests be written as a genuine
  negative control (all four fail against the pre-fix gate with the exact reported crash).

**The generalisable finding**, captured to the lessons store as
`gate-coverage-is-where-it-runs-times-what-it-is-handed`: a gate's coverage is the intersection
of *where it runs* and *what that invocation hands it*. Five gates in this repo had all three
intersections empty — pre-commit gets **staged** files (template-shipped files are never edited
downstream, so never staged); the generated project's CI needs a project pushed since the code
landed; and BlueprintX's own `--root .` run inspects a tree with no `src/`. `bin/lint.sh` is the
fix because `bin/ci/scaffold_lint_test.sh` runs it against a real scaffold.

Notes:

- #237 is the **only active false-green** in the queue: `check-provenance` is a CI job with no
  local equivalent, so "green locally, red in CI" is reachable today on the gate whose job is
  stopping an unprovenanced bronze row. Not a regression from #236 — the migration put the
  question in front of someone, it did not change the answer.
- #237's `hadolint` step is the non-trivial part: it runs as a Docker image, so it needs the
  resolve-or-skip contract `bin/lint_actions.sh` already implements, **including failing when
  discovery matches zero files** and an env flag that makes the skip impossible in CI.
- #111 and #238 both end in "a gate exists now" — so #111's should-fail requirement should be
  satisfied *by* the new gates in the same wave, not retrofitted after.

### Wave B — review gate

`templates/python-common/bin/check_review_threads.py` + `pr_gate`. **Order is load-bearing.**
(That path is the *outcome* of #217 below — the wave opened against `bin/ci/check_review_threads.py`
and a second, identical copy at the path now named. There is one file.)

- [x] #217 — one implementation, not two copies — **done**, the repo copy is deleted
- [x] #218 — the gate accepts a roster member declared `posts: status` — **done**, 5/5 tiers green
- [ ] #263 — a stale failed run of the gate blocks the PR forever *(filed from #218's own PR)*
- [ ] #220 — a review of a superseded commit satisfies the gate
- [ ] #196 — outdated review threads silently drop out of the merge block
- [ ] #234 — the reviewer roster declares three but only one can review

Without #217 first, each of #218/#220/#196 is fixed twice, once per copy — and the second copy
is exactly where the fix gets forgotten. That ordering constraint is now discharged:
`.github/workflows/review_threads.yml` runs `templates/python-common/bin/check_review_threads.py`
directly, and there is one file to edit for the remaining four.

**What #217 measured, and three ways the issue's own text was stale** — the same pattern this
ledger records for #111 and #254, now three-for-three:

- **The copies were byte-identical.** The issue describes a 5-line comment drift (repo copy citing
  PR #180, template copy citing `bin/enable_repo_rules.sh`); it had already been reconciled, so
  the "reconcile the two wordings" scope item had nothing left to do.
- **`--root` was the wrong instrument, not just an unnecessary one.** #189 gave that flag to
  `check_function_length.py` because it walks a filesystem tree and needs to be told which. This
  gate takes its subject from `GITHUB_REPOSITORY`/`PR_NUMBER` and reads the roster from
  `pathlib.Path.cwd()` — so invoking the template copy from the repo root already audits this
  repo, and adding a flag would have added argument-parsing surface to buy nothing.
- **One caller, not four.** The issue lists the workflow, the pre-commit hook, and
  `make`/`tasks.sh` targets. Grepping all three for `review` returns zero matches: only the
  workflow ever invoked it.

**What #218 measured, and the second defect the issue did not name.** Four-for-four on issue text
going stale: #218 cites `bin/ci/check_review_threads.py:167`, a file #217 deleted the day before.

- **The negative control reproduces the hole exactly.** Handed the full roster,
  `find_missing_review_problem` returns `None` for a review authored by `github-actions` — a
  pass. Handed `reviewer_logins(...)`, the same input fails. Both measured before the fix was
  called done, because "the tests are green" and "the bug was there" are different claims.
- **The `posts:` default had no safe direction, so there is none.** Reading a forgotten field as
  `status` makes the gate unsatisfiable (and unsatisfiable gates get bypassed with `--admin`,
  taking the real blocks with them); reading it as `threads` re-opens the hole the field exists
  to close. So `posts:` is now **required**, and an unrecognised value raises naming the row and
  the value. No row in this repo or the template lacked it, so nothing in the wild broke.
- **A roster of only `status` members is rejected at load.** It is not a no-op — it is a required
  check that can never go green, which is the fastest way to teach people that red means nothing.
- ⚠️ **The PR-author exemption was a second instance of the same defect, and the issue does not
  mention it.** `if pr_author in set_roster: return None` exempted *every* roster member, so a PR
  opened by `github-actions[bot]` skipped the check entirely. But that author cannot review, so a
  real reviewer CAN look at its PR: the exemption is "do not ask X to review X", never "bots are
  exempt". It narrowed with the parameter. This is the argument for fixing at the shared function
  rather than the reported call site — the ticket named one caller of one wrong set, and the wrong
  set was read twice.

**Two things #218's own PR taught, both from the gate policing itself:**

- **Review found a Major the fix introduced, in the same defect class the file already guards.**
  `reviewers: []` parsed to `{}`, which `main()` reads as "not adopted here" and exits 0 — the
  file is present, so the default-branch deletion guard never fires. That guard was written
  against the *mechanism* (deletion) rather than the *effect* (a roster with nobody in it), which
  is exactly why it missed the second door. Fixed in the same PR with a regression test. This is
  the second consecutive wave PR where review found a real defect behind a green matrix (#231 was
  the first), and both times the defect was in the fix rather than in the code it touched.
- ⚠️ **A stale failed run of this gate BLOCKS the merge button even after later runs pass** —
  filed as **#263**. Measured on #262: one `failure` at 14:26:58 (push-time, before the thread
  was answered) plus **seven** `success` runs at 14:27 on the same head still read
  `mergeStateStatus=BLOCKED, statusCheckRollup=FAILURE`. Re-running only the stale failure
  flipped it to `CLEAN`/`SUCCESS` with no other change. The re-trigger design is correct (it is
  what fixes #180); its **accumulation** in the rollup is not. This matters more than it looks
  because this is the ONE required check on the ruleset, so its stale red can block every PR —
  and it is indistinguishable from a genuinely unanswered thread.

⚠️ **The roster is still in two places and that is NOT the same defect.** The root
`.review-bots.yaml` is this repo's own data; `templates/python-common/.review-bots.yaml` is the
shipped default. They are byte-identical today because this repo's reviewers happen to be the
default set — a coincidence of values, not a copy of an implementation. Merging them would make
the template's default un-overridable by the very projects it ships to.

### Wave C — en-US prose

- [ ] #194 — the tracked rule still permits locale prose, contradicting the en-US policy
- [ ] #195 — translate the pt-BR ledgers to en-US
- [ ] #197 — prune the codespell ignore-list once repo prose is en-US
- [ ] #241 — state the Makefile↔tasks.sh sync rule locally
- [ ] #247 — make the docs locale a scaffold choice; run the language gate on BlueprintX itself
- [ ] #245 — evaluate `typos` as a **replacement** for codespell; fix `_com_download_attch`

Order: **#194 → #195 → #247 → #245.** Both of the last two are measurements that only become
meaningful over an en-US tree.

Measured 2026-08-23, over the same 331 tracked files: codespell reports 6 findings (all false
positives), `typos` reports 145 — of which **122 are in `docs/`**, overwhelmingly the pt-BR
ledgers #195 exists to translate. Portuguese in actual source code: **zero**. Adopting a second
speller before Wave C means hand-writing an ignore-list for text that is about to be deleted.

Two structural notes that came out of that measurement:

- **codespell cannot see inside identifiers.** It tokenizes on `\w+`, and `_` is inside `\w`, so
  a snake_case name misspelling "length" is **one token** and never matches the dictionary entry
  for the bare word. camelCase has no separator at all. (Demonstrated accidentally while writing
  this ledger: an earlier draft spelled the misspelling out on its own, and the codespell hook
  caught *that* instance while remaining blind to the compound one two words away.)
  Measured on a sample: identifiers 0/5 for codespell, 4/5 for typos. This matters
  disproportionately here because the type-prefix convention (`str_`, `df_`, `list_`) makes
  nearly every name a compound. Live proof in shipped source: `_com_download_attch`.
- **The language gate already exists and is language-agnostic by construction.** #247 is
  therefore wiring and parameterisation — the locale becomes a scaffold-rendered `exclude:` line
  — not a new detector. The gate is calibrated against a measured 18-false-positive first draft;
  rewriting it would be the expensive way to get less.

### Wave F — terminal UX and the palette

`bin/blueprintx.sh` + `bin/scaffold/*.sh` + the `bin/lib/common.sh` colour block. **One decision,
not three.**

- [ ] #256 — the banner and tagline ignore the logo's two-tone palette
- [ ] #253 — the menu's Cancel option is painted with the error colour
- [ ] #251 — show question hierarchy in the scaffolder prompts (70 of 72 uncoloured)

These share files, which is this ledger's usual grouping axis — but here the binding constraint is
stronger than blast radius: **each issue independently proposes pink for a different meaning.**

| Issue | Wants pink for |
|---|---|
| #256 | the brand — the `X` glyph and `Expansible.` |
| #253 | the Cancel control (`✕`) |
| #251 | the sub-question level in prompts |

Settled apart, they ship one colour carrying three unrelated meanings — precisely the defect #253
is filed against, tripled. And the existing palette is already overloaded: `MAGENTA` is bound to
`debug`/`section` in `print_status` **and** already paints the tagline, so "just use MAGENTA" is
not available to any of them. (There is no `step` level — the seven are
`success|error|warning|info|config|debug|section`, and `print_status` routes anything else to a
`*)` branch that names the bad status on stderr. That branch exists because 35 calls across the
five Python scaffolds were spelled `warn`, each rendering as unmarked chatter.)

**Order:** decide the token set and what each token MEANS first — brand accent vs. status level vs.
prompt depth are three different palettes that happen to share a hue family. The three issues are
mechanical once that is written down. ⚠️ 256-colour support is the open question underneath:
every existing token is 4-bit ANSI, the brand colours have no 4-bit equivalent, and
`bin/lib/common.sh` has **no tty guard and no `NO_COLOR` support** — escapes are emitted even into
a pipe. A fallback is part of the decision, not a follow-up.

Adjacent, deliberately NOT in this wave: **#250** (docs-site brand assets) shares the logo as its
source of truth and should consume whatever hexes this wave settles, but it touches `docs/` and
`mkdocs.yml` — no scaffold-test cost to amortise, so by this ledger's own rule it does not belong.
